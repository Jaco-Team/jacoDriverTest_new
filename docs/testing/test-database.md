## Когда использовать

Изменения действий с заказами, времени, кассы, статистики, прав и сохранения
настроек проверяем через настоящий локальный Laravel API, подключённый к тестовой
MariaDB, под отдельным тестовым курьером. Это проверяет реальные запросы и записи.
Демо-аккаунт остаётся полезным для внешнего вида, фикстур карты и отдельных
UI-состояний; его результат не подтверждает запись времени, кассы и статистики в БД.
Unit-тесты с заглушками выполняются отдельно и также не заменяют этот сценарий.

Маршрут данных:

```text
Сайт :3225 / Android / iPhone
  → локальный Laravel API http://localhost:8080
  → тестовая MariaDB 95.163.229.158:3306
  → отдельный тестовый курьер и его помеченные заказы
```

Локальный URL API и тестовая БД — два отдельных выбора. `localhost:8080` может
обслуживать API, подключённый к боевой БД. До любых действий проверяем настройки
и `main`, и `system` в Laravel, а не только адрес в браузере или приложении.

## 1. Настроить локальный API на тестовую БД

Перед переключением сохраните приватную копию действующего `.env`, не затирая
прежние резервные копии. На этом Mac уже есть
`/Users/denis/Public/work/laravel-api-driver/.env.before-test-db-20261120`:
это приватная резервная конфигурация, а не шаблон для тестового запуска.

Рабочие несекретные параметры согласованной среды:

```dotenv
APP_ENV=local
APP_URL=http://localhost:8080
APP_TIMEZONE=Europe/Samara
APP_PORT=8080
DB_CONNECTION=main
DB_URL=

MAIN_DB_DRIVER=mariadb
MAIN_DB_HOST=95.163.229.158
MAIN_DB_PORT=3306
MAIN_DB_DATABASE=jaco_main_rolls
MAIN_DB_URL=
MAIN_DB_SOCKET=

SYSTEM_DB_DRIVER=mariadb
SYSTEM_DB_HOST=95.163.229.158
SYSTEM_DB_PORT=3306
SYSTEM_DB_DATABASE=jaco_main_rolls
SYSTEM_DB_URL=
SYSTEM_DB_SOCKET=

SESSION_DRIVER=file
CACHE_STORE=file
DRIVER_STATIC_CACHE_STORE=array
DRIVER_STATISTICS_CACHE_STORE=array
```

`MAIN_DB_USERNAME`, `MAIN_DB_PASSWORD`, `SYSTEM_DB_USERNAME`, `SYSTEM_DB_PASSWORD`
заполняются приватными тестовыми реквизитами. Не подставляйте боевые реквизиты.
В этой конкретной тестовой среде **оба подключения используют `jaco_main_rolls`**:
отдельная `laravel_driver` там не была доступна. Это отличается от общей инструкции
Laravel, где `system` обычно указывает на `laravel_driver`. Автоматически создавать
её или переносить этот тестовый выбор в production не нужно. Базы кафе
`jaco_rolls_1` … `jaco_rolls_8` используют тестовый адрес из `MAIN_DB_*`;
конкретное кафе выбирается доступом тестового пользователя.

Используйте локальный Sail с `compose.yaml`, не production `docker-compose.yml`.
Если API ещё не запущен, пользователь запускает его отдельным шагом:

```bash
cd /Users/denis/Public/work/laravel-api-driver
COMPOSE_FILE=compose.yaml ./vendor/bin/sail up -d laravel.test
```

После изменения `.env` пользователь сбрасывает только кэш конфигурации и
перезапускает локальный процесс, чтобы он прочитал новый адрес БД:

```bash
COMPOSE_FILE=compose.yaml ./vendor/bin/sail artisan config:clear
COMPOSE_FILE=compose.yaml ./vendor/bin/sail restart laravel.test
```

После запуска сверяйте в эффективной конфигурации процесса только `driver`,
`host`, `port`, `database` подключений `main`, `system` и выбранного кафе.
Для вывода только этих полей используйте отдельный шаг:

```bash
COMPOSE_FILE=compose.yaml ./vendor/bin/sail artisan tinker --execute='foreach (["main", "system", "jaco_rolls_1"] as $name) { dump([$name => array_intersect_key(config("database.connections.".$name), array_flip(["driver", "host", "port", "database"]))]); }'
```

Замените `jaco_rolls_1` на tenant выбранного кафе, если он другой.
Не выводите весь объект подключения с паролем. Текст `.env` недостаточен, если
остался кэш конфигурации или окружение процесса переопределяет файл. В локальном
`compose.yaml` уже есть `artisan serve --no-reload` — эту настройку сохраняем.

Миграции, `migrate:fresh`, seed всей БД, массовые UPDATE/DELETE и правки общих
ролей/настроек не являются частью этой подготовки. На тестовом сервере тоже есть
чужие данные: используем только собственный помеченный набор. Инструкция описывает
команды пользователя; агент сам не запускает серверы, сборки, тесты или операции
с БД, если такого разрешения нет в текущей задаче.

## 2. Создать или продолжить отдельный тестовый набор

Сначала прочитайте существующий state-файл приватно. Он нужен и для входа, и для
точной очистки; **не удаляйте его ради повторного `create`**.

| Состояние                                     | Действие                                                                                                       |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Файла нет, создание нового набора согласовано | Выполнить `create` один раз                                                                                    |
| `phase=created`                               | Продолжить этот набор, прочитать `status`; завершённые заказы не переоткрывать                                 |
| `phase=prepared`                              | Остановить запись, сверить сохранённые ID и результат транзакции; не повторять создание вслепую                |
| `phase=cleaned`                               | Набор уже удалён; для нового цикла после проверки архивировать этот очищенный state и затем выполнить `create` |

Создание отдельным шагом:

```bash
/opt/homebrew/opt/php@8.5/bin/php /Users/denis/Documents/ChatGPT/Driver/test-offline-orders.php create
```

Скрипт проверяет тестовый адрес/порт, `APP_ENV=local`, `DB_CONNECTION=main`,
оба подключения и отсутствие URL/socket-переопределений. Создаёт нового курьера,
личные права доступа к одному существующему кафе и три его заказа:
`WEB`, `ANDROID`, `IPHONE`. Общая роль курьера 8 должна уже давать доступ;
чужие права не исправляются под тест. ID и метка сохраняются до COMMIT,
операции сериализованы файловой блокировкой. При ошибке защитного условия
разбирают причину, а не отключают проверку.

Заказы уже назначены этому курьеру (`status_order=5`) и видны в **«Мои отмеченные»**.
Пустые «Активные» при таком наборе не означают ошибку. График для завершения уже
назначенных заказов не нужен. Метка `OFFLINE_CHECK_…`, адрес «ТЕСТ … — НЕ ДОСТАВЛЯТЬ»,
технический телефон и сумма 100 ₽ отличают их от рабочих заказов. Реальных клиентов,
состава и адресов доставки в этих фикстурах нет. Отсутствие координат назначения
даёт дистанцию 0 для существующего правила среднего; GPS-условия клиента сохраняются.

Текущий скрипт предназначен **для завершения назначенных заказов**. Он не является
универсальным генератором для взятия, отмены, оплаты и графика. Для другой правки
нужны подходящие отдельные фикстуры, их учёт и очистка. Не используйте оставшийся
заказ другой платформы и не возвращайте завершённый заказ в статус 5 ради повтора.
Сначала подготовьте новый учитываемый набор или расширение скрипта; текущие
валидаторы допускают исходные 3/7 записей, расширение мобильными партиями (11/15), набор 19 после WEB-повтора 27 после отдельной проверки мобильных стилей и 30 после трёх заказов RETRY.

Для проверки очереди из четырёх заказов есть однократное расширение этого набора:

```bash
/opt/homebrew/opt/php@8.5/bin/php /Users/denis/Documents/ChatGPT/Driver/test-offline-orders.php add-web-batch
```

Оно добавляет только `WEB-2` … `WEB-5` тому же курьеру и включает их в `status`
и `cleanup`. Повторное добавление запрещено. В текущем наборе 20.11.2026 оно
уже выполнено. Эта WEB-партия подтвердила сохранность данных; её не считаем
непроведённой проверкой. Отдельно остаётся повтор сайта с пересобранным preview
после настройки локального ожидания 45/60 секунд: прежняя ручная партия прошла
на версии с лимитом 15 секунд и временными ошибками. Для такого повтора нужны
новые WEB-фикстуры. Команда однократного повтора после создания мобильных партий:

```bash
/opt/homebrew/opt/php@8.5/bin/php /Users/denis/Documents/ChatGPT/Driver/test-offline-orders.php add-web-recheck
```

Добавляет только `WEB-RECHECK-1` … `WEB-RECHECK-4` из существующего набора 15 → 19.
Старые заказы и реквизиты не меняются, все новые включены в `status`/`cleanup`.
Повторное создание запрещено. На момент подготовки команда ещё не запускалась.

Для оставшихся пакетных проверок Android/iPhone подготовлена отдельная команда:

```bash
/opt/homebrew/opt/php@8.5/bin/php /Users/denis/Documents/ChatGPT/Driver/test-offline-orders.php add-mobile-batches
```

Она однократно добавляет **8** заказов тому же тестовому курьеру:

Старые записи и реквизиты не меняются. После выполнения из текущего набора 7

свежего статуса, четыре исходных времени и ровно одну кассовую запись на каждый
заказ. Не завершайте заказы другой платформы. Итоговую статистику сверяйте с
выдачей и датой/временем кассы всех включённых в среднее заказов.

### Android: самостоятельная локальная Release-сборка

```bash
cd /Users/denis/Public/work/jacoDriverTest_new
SENTRY_DISABLE_AUTO_UPLOAD=true JACO_LARAVEL_API=local npm run android:build:local
```

Это выполненная пользователем схема сборки без Metro. Отключение загрузки

## 5. Ручная проверка изменения и чтение результата

Сначала загрузите нужный заказ онлайн в «Мои отмеченные». Для офлайн-завершения:

1. Отключите интернет у клиента. В Android включите авиарежим и выключите Wi-Fi;
   интернет Mac и локальный API оставьте работающими. Дождитесь плашки отсутствия сети.
2. Завершите только заказ своей платформы, запомните время подтверждения до GPS.
3. Дождитесь «Завершение сохранено. Ожидает отправки».
4. Не возвращая сеть, перезагрузите страницу сайта или полностью закройте приложение.
   Для тестовой Android-установки использовалась команда ниже. Снова откройте клиент
   без сети и убедитесь, что ожидание сохранилось.
5. Верните сеть и оставьте клиент открытым. Повторно завершать заказ не нужно.
6. Дождитесь «У клиента» и сравните «Отдали» со временем исходного подтверждения.
   После правки приложения отправленное завершение показывает
   «Завершение отправлено. Обновляем статус», без возврата кнопок до свежего статуса.
7. Отдельно прочитайте данные в БД через `status`, затем проверьте нужную статистику.

```bash
adb -s emulator-5554 shell am force-stop com.jacodrivertest.localtest
```

Проверка записей созданного набора, без изменений данных:

```bash
/opt/homebrew/opt/php@8.5/bin/php /Users/denis/Documents/ChatGPT/Driver/test-offline-orders.php status
```

`status` использует read-only транзакцию. Для каждого заказа выводит платформу,
статус, выдачу, завершение, связанные кассовые записи и `elapsed_seconds`.

| Что проверяем            | Ожидаемый результат                                                            |
| ------------------------ | ------------------------------------------------------------------------------ |
| До завершения            | `status_order=5`, `cash_count=0`                                               |
| После отправки           | `status_order=6`, `cash_count=1`                                               |
| Время завершения и кассы | Исходное подтверждение, а не время возврата сети или ответа API                |
| Касса этой фикстуры      | 100 ₽ у созданного курьера, одна запись                                        |
| Длительность             | Дата/время кассы минус полная дата/время выдачи                                |
| Повтор исходного запроса | То же время и одна касса; для такого повтора сохраняют исходный `completed_at` |

`orders.close_date_time_order` — **TIME**, не DATETIME. Полная дата завершения
берётся из `order_driver_cash.date` и `time`; поэтому для перехода через полночь
и статистики нельзя вычитать только часы. Часовой пояс API — Europe/Samara,
клиент отправляет `completed_at` в UTC. Каждый заказ и каждую платформу
проверяйте отдельно. Общее среднее пересчитывайте по реально включённым заказам;
старое значение до добавления ещё одного завершения уже не является эталоном.

Локальная отправка может задержаться из-за локального Laravel/БД. Сохранённое
завершение в клиентах ждёт local API до 45 секунд, прокси сайта до 60 секунд;
для production осталось 15 секунд. Это предел ожидания, не искусственная пауза
и не ускорение Laravel. Не связывайте все ошибки с одним таймаутом без статуса,
тела ответа и времени запроса. Локальная проверка не измеряет скорость production.

## 6. Очистка после завершения всех нужных проверок

Сначала сохраните результаты и убедитесь, что в клиентах не осталось неотправленных
команд. Не удаляйте набор, пока нужен незавершённый заказ другой платформы.
Очистка — отдельное согласованное действие пользователя:

```bash
/opt/homebrew/opt/php@8.5/bin/php /Users/denis/Documents/ChatGPT/Driver/test-offline-orders.php cleanup
```

Скрипт сверяет ID, метки, владельца и отсутствие посторонних заказов у тестового
курьера. В транзакции удаляет только созданные заказы, их результаты завершения,
связанную историю, токены и созданного курьера с личными записями доступа/настроек.
Он не сбрасывает AUTO_INCREMENT, не удаляет серверные журналы и не чистит всю БД.
После успеха state остаётся с `phase=cleaned`, пароль курьера из него убирается.
Если guard остановил очистку, не удаляйте state и не заменяйте её широким SQL.

Для следующего полного цикла архивируют уже очищенный state, затем создают новый
набор. После завершения работы с тестовой средой восстановление прежнего `.env`
делают отдельным шагом со сбросом кэша конфигурации и перезапуском процесса;
оно не является автоматической частью cleanup. Проверяйте, куда теперь направлены
клиенты, прежде чем продолжать действия. Ничего публиковать для этого не требуется.
