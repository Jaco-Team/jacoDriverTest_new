# Правила unit-тестирования

## Цель документа

Этот документ фиксирует правила для unit/component-level тестов в `jacoDriverTest`.

Существующий Jest-набор — обязательный baseline. Его нужно сохранять и дополнять
проверками поведения, а не переписывать систему или ослаблять сценарии ради
зелёного результата. Свежий статус ведётся в [журнале тестирования](./testing-progress.md).

## Что тестировать unit-тестами

В этом проекте unit-тестами в первую очередь стоит покрывать:

- бизнес-ветки store;
- действия с заказом;
- GPS-ветвления;
- условия показа кнопок;
- закрытие модалок после успешных действий;
- форматирование карточки заказа;
- фильтрацию fake/dev данных;
- аналитику событий;
- нормализацию дат;
- updater-хуки без реальных интервалов в runtime.

## Что не тестировать unit-тестами

Unit-тесты не должны:

- ходить в реальный backend;
- требовать реальный iOS Simulator или Android Emulator;
- требовать реальную карту;
- требовать реальные push-уведомления;
- создавать реальные заказы;
- зависеть от текущей даты без фиксации времени;
- зависеть от порядка запуска других тестов.

## Работа с API

API в unit-тестах должен быть замокан или переведен в безопасный fake/dev режим.

Особенно важно:

- не выполнять реальные действия с заказом;
- не проверять production-сценарии через реальные финальные API-действия;
- сохранять guard-тесты, которые защищают production от fake-флагов.

## Работа с fake timers

В проекте уже используется [jest.setup.ts](../../jest.setup.ts), где включены fake timers.

Правила:

- если тест сам включает `jest.useFakeTimers()`, он должен явно чистить состояние после себя;
- для `jest.setSystemTime` лучше использовать значение в миллисекундах, если текущая связка Jest/fake-timers этого требует;
- после тестов с таймерами использовать `jest.runOnlyPendingTimers()` или `jest.clearAllTimers()`, если есть риск хвостов;
- не смешивать real timers и fake timers без необходимости.

## Работа с React Native моками

В проекте много ручных моков:

- [__mocks__](../../__mocks__)
- [jest.setup.ts](../../jest.setup.ts)

Правила:

- не ломать существующие моки ради одного теста;
- если новый компонент требует нативный модуль, сначала добавить узкий мок;
- не подключать реальные нативные реализации в unit-тестах;
- если мок становится общим, держать его в `__mocks__` или `jest.setup.ts`.
- моки `Pressable`/`TouchableOpacity` должны учитывать `disabled`, responder,
  accessibility и callback-стили; не вызывать напрямую `onPress` неактивной кнопки;
- переданные иконке цвет и толщину проверять через публичные props, а не через
  внутреннее устройство mock-компонента;
- изменение общего мока сопровождать его узким регрессионным тестом, не заменяя
  существующие бизнес-сценарии проверкой одной заглушки.

## Асинхронные component-тесты

Проект использует React Native Testing Library 14. В новых и изменяемых тестах
ожидать завершения асинхронных `render`, `renderHook`, `rerender`, `unmount`,
`fireEvent` и `act` по контракту API,
а также запущенных ими запросов/обновлений состояния. Не оставлять незавершённую
операцию следующему тесту и не исправлять такую гонку произвольной задержкой.

Для таймеров использовать управляемое продвижение времени и проверять нужное
состояние после завершения действия. Для запоздалых ответов явно моделировать
смену аккаунта/кафе или новый запрос и проверять, что старый callback не меняет
текущий экран. Unit-тест не должен ходить в настоящий API.

## Контракты сборки и iOS-зависимостей

[Проверки RN-версий](../../__tests__/ios-rn-version.test.ts) и
[workflow Pods](../../__tests__/ios-pods-workflow.test.ts) используют временные
файлы и заглушки команд. Контракт сохранённого `Podfile.lock` работает на чистом
CI без `Pods`. Эти тесты не устанавливают SDK, не обновляют зависимости и не
доказывают успешную нативную сборку. Проверка установленного ядра перед
`npm run ios` и настоящая сборка — отдельные шаги, описанные в [README](../../README.md).

## Где хранить тесты

Текущий проектный паттерн:

- тесты лежат в [__tests__](../../__tests__);
- имена файлов описывают сценарий;
- UI-тесты компонентов имеют префикс `ui.*`;
- store/flow тесты описывают бизнес-действие.

Этот паттерн можно продолжать, пока не появится отдельная задача на перенос тестов рядом с модулями.

## Минимальное правило для новой бизнес-логики

Если изменение затрагивает:

- заказ;
- действие курьера;
- GPS-ветку;
- карту заказов;
- авторизацию;
- настройки;
- статистику;
- API guards;

нужно добавить или обновить unit-тест.

## Минимальная команда проверки

Эквивалентная явная команда Jest:

```bash
npm test -- --runInBand --watchman=false
```

Текущая baseline-команда:

```bash
npm run test:unit
```

## Проверки команд запуска и установки Pods

[Android workflow](../../__tests__/android-workflow.test.ts),
[iOS workflow](../../__tests__/ios-pods-workflow.test.ts) и
[проверка версий iOS](../../__tests__/ios-rn-version.test.ts) входят в Jest-набор.
Они используют временные проекты и подставные инструменты. Android-фикстура
изолирует также абсолютные пути поиска JDK и пустой `JAVA_HOME`, чтобы не
запустить настоящий Java на CI. Меняются только пути файловой границы в копии
скрипта, не ветвления или ожидаемое поведение проверяемых команд.
Зелёный workflow-тест не подтверждает настоящую нативную сборку.

## Нативные регрессии маркеров

JS-моки не проверяют состояние Fabric/MapKit. Для загрузки изображений и повторного
использования нативных меток есть отдельные тесты, исполняющие реальные тела
методов установленного `react-native-yamap-plus` с управляемыми callback:

```bash
npm run test:native:markers
npm run test:native:markers:ios-images
npm run test:native:markers:android
```

iOS-тестам нужны macOS и Xcode Command Line Tools. Android-тесту нужны Java 17+
и Kotlin compiler из существующего Gradle cache после обычной сборки Android.
Тесты работают без телефона, эмулятора, API-запросов и загрузки новых зависимостей.
Они проверяют recycle, A → B → A → B, устаревшие callbacks, detach/reattach,
ошибку декодирования и отсутствие бесконечного retry. Проверку отрисовки и точных
нажатий на экране нужно выполнять отдельно на устройстве или эмуляторе.
