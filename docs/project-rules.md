# Правила работы с проектом

## Цель документа

Этот документ фиксирует рабочие правила для разработки в `jacoDriverTest`.

Он нужен, чтобы:

- изменения были предсказуемыми;
- рискованные зоны затрагивались осознанно;
- проект не становился хаотичнее;
- проверки `lint`, `typecheck` и unit-тестов постепенно стали обязательным baseline.

## Главный принцип

Изменения должны быть локальными, понятными и проверяемыми.

Для этого проекта особенно важно:

- не смешивать фичу, рефакторинг и настройку инфраструктуры без необходимости;
- сначала понять, какой store или экран затрагивается;
- помнить, что заказ, карта, геолокация и startup связаны сильнее, чем кажется по папкам;
- не добавлять новый подход, если уже есть рабочий локальный паттерн.

## Правило 1. Не делать лишние изменения

Если задача локальная, изменение тоже должно оставаться локальным.

Без явной причины не нужно:

- переписывать соседний код;
- менять архитектурный подход;
- править unrelated-файлы;
- менять форматирование большого файла ради маленькой правки;
- переносить код между слоями.

## Правило 2. Сначала определить слой

Перед правкой нужно понять, к какому слою относится задача:

- `app`
- `processes`
- `features`
- `entities`
- `shared`
- `components/ui`
- `analytics`
- `ios`
- `android`

Если изменение затрагивает модули store в [src/shared/store](../src/shared/store), [App.tsx](../App.tsx), [index.js](../index.js), [src/features/orders-map](../src/features/orders-map) или [src/features/orders-list](../src/features/orders-list), его нужно считать потенциально рискованным.

## Правило 3. Осторожно работать с глобальными store

Глобальные store в этом проекте - одна из самых чувствительных зон.

Правила:

- не менять store без понимания соседних сценариев;
- после изменения store проверять не только целевую фичу;
- не раздувать store новой логикой, если ее можно оставить локальной;
- для бизнес-веток добавлять или обновлять unit-тесты;
- при спорной логике сначала покрывать текущее поведение тестом.

## Правило 4. Заказы считаются production-sensitive зоной

К заказам относятся:

- список заказов;
- карта заказов;
- карточка заказа;
- действия курьера;
- QR/оплата;
- fake/order-cancel/finish/take ветки;
- GPS-условия действий.

Здесь нельзя менять поведение "по ощущениям".

Минимальная проверка после изменений:

- релевантный unit-тест;
- ручная проверка целевого сценария;
- проверка соседней ветки, если логика условная.

## Правило 5. Осторожно работать со startup

Startup включает:

- [index.js](../index.js)
- [App.tsx](../App.tsx)
- [src/app/navigation/MainDrawerNavigator.tsx](../src/app/navigation/MainDrawerNavigator.tsx)

Здесь инициализируются:

- Sentry;
- AppMetrica;
- YaMap;
- уведомления;
- updater-хуки;
- dev-флаги fake orders.

Правила:

- не добавлять side effects без необходимости;
- проверять запуск приложения после изменений;
- помнить про различия iOS и Android;
- не смешивать startup-правки с бизнес-логикой заказов.

## Правило 6. Осторожно работать с геолокацией и картой

Геолокация и карта завязаны на:

- permissions;
- platform-specific поведение;
- обновление позиции;
- масштаб карты;
- группировку заказов;
- маркеры и модалки.

После изменений нужно проверять:

- список заказов;
- карту;
- открытие заказа на карте;
- состояние без заказов;
- GPS-ветку действия, если она затронута.

GPS-ветка действий с заказом («Отменить», «Завершить», «Клиент не вышел на
связь» при `driver_need_gps`) работает как на сайте: 15 секунд точный GPS,
затем 10 секунд грубая позиция (`maximumAge` 60 секунд). Если позиция так и не
пришла, действие продолжается с координатами `0, 0`, как в `check_pos_fake`.
Запрет доступа и подменённая позиция по-прежнему останавливают действие.
Пока идёт ожидание, виден обратный отсчёт (`location_wait` в `useGEOStore`):
`LocationWaitCountdown` на общем спиннере — белое кольцо с крупной цифрой секунд
и подписью; на время ожидания оно заменяет обычный индикатор, затемнение то же,
что у спиннера. Спиннер рисуется поверх окна подтверждения действия,
поэтому в самом окне отсчёт не дублируем. Кольцо убывает от начала всего
ожидания (`firstStartedAt`), повторная попытка его не «перезаряжает». Иконки в
окнах берём из `lucide`: шрифты `react-native-vector-icons` в сборку iOS не
попадают. Фоновое сохранение позиции без координат на сервер ничего не
отправляет.

Как на сайте, при возвращении приложения из фона открытый экран списка или
карты сразу запрашивает заказы (`useOrdersRefreshOnForeground`), не дожидаясь
таймера: так уведомление об отменённых заказах появляется без задержки.

Пункты меню «среднее время» и «Статистика» включаются настройками кафе. Как на
сайте, приложение передаёт выбранное кафе в запрос настроек и при смене кафе
(`refreshMenuFlags`), и при обычном обновлении (`getSettings`): иначе следующее
обновление вернуло бы флаги домашней точки. Флаги из ответа для другого кафе не
применяются.

## Правило 7. Fake/dev режимы не должны попадать в production

В [index.js](../index.js) есть dev-флаг:

```ts
global.__FAKE_ORDERS__ = 'off';
```

Правила:

- fake-режимы использовать только осознанно;
- production-поведение не должно зависеть от dev-флагов;
- guard-тесты для fake-логики сохранять и обновлять при изменениях.

## Правило 8. Тесты должны защищать бизнес-поведение

В проекте уже есть полезный набор unit-тестов в [__tests__](../__tests__).

Особенно ценны тесты, которые фиксируют:

- действия с заказом;
- GPS-ветвления;
- закрытие модалок;
- аналитику;
- фильтрацию fake orders;
- форматирование карточки заказа;
- статистику;
- updater-интервалы.

При изменении этих зон тесты нужно обновлять вместе с кодом.

## Правило 9. Сохранять обязательный quality baseline

`lint`, `typecheck` и unit-тесты уже являются обязательным baseline:

```bash
npm run lint
npm run typecheck
npm run test:unit
```

При падении сначала выяснять причину и исправлять её в согласованном scope.
Не удалять сценарии, не ослаблять проверки и не добавлять `skip` ради зелёного
результата. Разрешение на запуск проверок и ручной smoke по-прежнему определяется
правилами ролей и запросом пользователя.

Эти проверки не заменяют нативные регрессии, сборки и ручные сценарии Android/iOS.
План первоначальной стабилизации сохранён в журнале как история, а свежие
результаты — в [статусе тестирования](./testing/testing-progress.md).

Подробно:

- [docs/quality-baseline.md](./quality-baseline.md)

## Правило 10. Документацию обновлять вместе с важными изменениями

Рабочий порядок агента — роли Cursor в `.cursor/rules`. Если роль устарела или мешает, её нужно править, а не обходить.

Документацию нужно обновлять, если меняются:

- структура проекта;
- правила работы;
- тестовый процесс;
- обязательные команды;
- критичные бизнес-сценарии;
- fake/dev режимы;
- release checklist.

## Как принимать решение в спорной ситуации

Если есть выбор между быстрым, но рискованным изменением и более аккуратным понятным изменением, для этого проекта по умолчанию выбирается более аккуратный путь.

## Вход и восстановление пароля

Экраны `Auth` и `ResetPwd` выглядят и работают как страница входа SSO и ШЭФ:
карточка по центру, подписи над полями, номер маской `+7 (999) 123-45-67`.
Общие части — в `src/shared/ui/auth` (`AuthSsoKit`, `AuthTextField`,
`AuthScreenLayout`, `authPalette`); размеры и цвета взяты со страницы входа SSO
(`laravel-api-driver/resources/views/idp/partials/styles.blade.php`), при
изменении оформления правьте оба места. В светлой теме цвета те же, что на
странице SSO, в тёмной нейтральные берутся из темы приложения. Шрифт остаётся
Roboto: Inter в приложение не добавлялся.

Восстановление идёт по шагам «номер и способ получения кода → код из 6 цифр →
новый пароль → готово» (`useResetPwdLogic`) через
`/api/v1/auth/password/recovery/channels`, `request-code` и `reset`. Код сервер
проверяет вместе с новым паролем; неизвестный номер показывается под полем.
Способы получения кода и необходимость CAPTCHA приходят с сервера; без ответа
остаётся SMS с обязательной CAPTCHA. После смены пароля кнопка «Войти» входит с
новым паролем. Прежние методы хранилища `sendSMS` и `sendCode` и маршруты
`send-code`/`confirm-code` из приложения удалены.
