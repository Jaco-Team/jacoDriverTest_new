# Правила работы с проектом

## Цель документа

Этот документ фиксирует рабочие правила для разработки в `jacoDriverTest`.

Он нужен, чтобы:

- изменения были предсказуемыми;
- рискованные зоны затрагивались осознанно;
- проект не становился хаотичнее;
- проверки `lint`, `typecheck` и unit-тестов постепенно стали обязательным baseline.

## Главный принцип

Изменения должны быть локальными, понятными и проверяемыми.

Для этого проекта особенно важно:

- не смешивать фичу, рефакторинг и настройку инфраструктуры без необходимости;
- сначала понять, какой store или экран затрагивается;
- помнить, что заказ, карта, геолокация и startup связаны сильнее, чем кажется по папкам;
- не добавлять новый подход, если уже есть рабочий локальный паттерн.

## Правило 1. Не делать лишние изменения

Если задача локальная, изменение тоже должно оставаться локальным.

Без явной причины не нужно:

- переписывать соседний код;
- менять архитектурный подход;
- править unrelated-файлы;
- менять форматирование большого файла ради маленькой правки;
- переносить код между слоями.

## Правило 2. Сначала определить слой

Перед правкой нужно понять, к какому слою относится задача:

- `app`
- `processes`
- `features`
- `entities`
- `shared`
- `components/ui`
- `analytics`
- `ios`
- `android`

Если изменение затрагивает [src/shared/store/store.ts](../src/shared/store/store.ts), [App.tsx](../App.tsx), [index.js](../index.js), [src/features/orders-map](../src/features/orders-map) или [src/features/orders-list](../src/features/orders-list), его нужно считать потенциально рискованным.

## Правило 3. Осторожно работать с глобальными store

Глобальные store в этом проекте - одна из самых чувствительных зон.

Правила:

- не менять store без понимания соседних сценариев;
- после изменения store проверять не только целевую фичу;
- не раздувать store новой логикой, если ее можно оставить локальной;
- для бизнес-веток добавлять или обновлять unit-тесты;
- при спорной логике сначала покрывать текущее поведение тестом.

## Правило 4. Заказы считаются production-sensitive зоной

К заказам относятся:

- список заказов;
- карта заказов;
- карточка заказа;
- действия курьера;
- QR/оплата;
- fake/order-cancel/finish/take ветки;
- GPS-условия действий.

Здесь нельзя менять поведение "по ощущениям".

Минимальная проверка после изменений:

- релевантный unit-тест;
- ручная проверка целевого сценария;
- проверка соседней ветки, если логика условная.

## Правило 5. Осторожно работать со startup

Startup включает:

- [index.js](../index.js)
- [App.tsx](../App.tsx)
- [src/app/navigation/MainDrawerNavigator.tsx](../src/app/navigation/MainDrawerNavigator.tsx)

Здесь инициализируются:

- Sentry;
- AppMetrica;
- YaMap;
- уведомления;
- updater-хуки;
- dev-флаги fake orders.

Правила:

- не добавлять side effects без необходимости;
- проверять запуск приложения после изменений;
- помнить про различия iOS и Android;
- не смешивать startup-правки с бизнес-логикой заказов.

## Правило 6. Осторожно работать с геолокацией и картой

Геолокация и карта завязаны на:

- permissions;
- platform-specific поведение;
- обновление позиции;
- масштаб карты;
- группировку заказов;
- маркеры и модалки.

После изменений нужно проверять:

- список заказов;
- карту;
- открытие заказа на карте;
- состояние без заказов;
- GPS-ветку действия, если она затронута.

## Правило 7. Fake/dev режимы не должны попадать в production

В [index.js](../index.js) есть dev-флаг:

```ts
global.__FAKE_ORDERS__ = 'off';
```

Правила:

- fake-режимы использовать только осознанно;
- production-поведение не должно зависеть от dev-флагов;
- guard-тесты для fake-логики сохранять и обновлять при изменениях.

## Правило 8. Тесты должны защищать бизнес-поведение

В проекте уже есть полезный набор unit-тестов в [__tests__](../__tests__).

Особенно ценны тесты, которые фиксируют:

- действия с заказом;
- GPS-ветвления;
- закрытие модалок;
- аналитику;
- фильтрацию fake orders;
- форматирование карточки заказа;
- статистику;
- updater-интервалы.

При изменении этих зон тесты нужно обновлять вместе с кодом.

## Правило 9. Quality baseline приводить к зеленому состоянию постепенно

Пока `lint`, `typecheck` и unit-тесты не все зеленые, их нельзя использовать как жесткий gate без подготовки.

Порядок:

1. Стабилизировать unit-тесты.
2. Добавить явный `test:unit`-скрипт.
3. Исправить текущие ошибки TypeScript.
4. Добавить `typecheck`-скрипт.
5. Оживить ESLint.
6. Сделать все три проверки обязательным baseline.

Подробно:

- [docs/quality-baseline.md](./quality-baseline.md)

## Правило 10. Документацию обновлять вместе с важными изменениями

Рабочий порядок агента — роли Cursor в `.cursor/rules`. Если роль устарела или мешает, её нужно править, а не обходить.

Документацию нужно обновлять, если меняются:

- структура проекта;
- правила работы;
- тестовый процесс;
- обязательные команды;
- критичные бизнес-сценарии;
- fake/dev режимы;
- release checklist.

## Как принимать решение в спорной ситуации

Если есть выбор между быстрым, но рискованным изменением и более аккуратным понятным изменением, для этого проекта по умолчанию выбирается более аккуратный путь.
