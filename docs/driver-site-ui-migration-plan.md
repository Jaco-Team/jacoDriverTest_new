# План переноса UI курьерского сайта в приложение

Дата создания: 27 августа 2026 года.

Ветка приложения: `new_architecture`. Ветка `main` этой работой не меняется.

Эталон:

- проект `jaco_driver_site`;
- ветка `api-laravel`;
- текущее состояние всей ветки `api-laravel`, а не отдельный зафиксированный коммит;
- рабочий сайт: [driver.jacochef.ru](https://driver.jacochef.ru/auth).

Перед каждым UI-этапом необходимо проверить, что `jaco_driver_site` находится
на ветке `api-laravel`, и заново изучить актуальные компоненты, стили, темы,
типы, API-контракты и связанные файлы этой ветки. Исторические коммиты, старые версии
файлов и ранее выписанные значения не используются как эталон.

Этот документ ведёт UI-миграцию отдельно от обновления React Native / Fabric. Технический фундамент и его ограничения зафиксированы в [docs/new-architecture-migration-plan.md](./new-architecture-migration-plan.md).

Перед началом экранной миграции фундамент зафиксирован на React Native `0.87.1`; совместимые зависимости обновлены внутри текущих major и проверены через lint, typecheck, unit, Android Debug и iOS Debug. Tailwind `3.4.19` и NativeWind `4.2.6` на этом этапе не менялись.

## 1. Цель

Перенести новый интерфейс курьерского сайта в React Native-приложение максимально близко визуально, но с корректной адаптацией под Android и iOS.

Это тот же курьерский продукт, а не новая бизнес-логика приложения.

Основные правила:

- переносить UI поэтапно, по одному согласованному экрану или связанному блоку;
- до начала каждого этапа фиксировать `In scope now`, `Out of scope` и критерии приёмки;
- код менять только после отдельного разрешения пользователя на конкретный этап;
- сохранять текущие API, store, токен, навигацию и аналитику, если их изменение отдельно не согласовано;
- не копировать MUI, SCSS и web-реализации буквально — переносить визуальный результат средствами React Native;
- не придумывать форматы данных, тексты, размеры, цвета, состояния или поведение: каждое значение должно подтверждаться актуальным проектом `jaco_driver_site` в ветке `api-laravel`;
- тестовые данные для визуальной проверки должны повторять форматы актуальных типов и API-контрактов сайта, а не создаваться произвольно;
- тесты сайта не копируются и не используются как шаблон; приложение сохраняет собственные unit/UI-тесты, соответствующие React Native и текущей мобильной логике;
- если нужное значение невозможно подтвердить по актуальному проекту или рабочему сайту, сначала зафиксировать неопределённость и согласовать её с пользователем;
- не добавлять новую зависимость без отдельного согласования;
- после этапа обновлять статус в этом документе;
- коммиты делает только пользователь.

## 2. Зафиксированные решения

### SSO и CAPTCHA

На этапе переноса авторизации:

- кнопка SSO должна присутствовать и визуально соответствовать сайту;
- нажатие на кнопку SSO ничего не выполняет;
- на начальном экране входа CAPTCHA не показывается; визуальная заглушка появляется только после ответа API `captcha_required`, но не загружается и не проверяется;
- визуальная CAPTCHA без интеграции предусматривается на первом шаге восстановления пароля;
- CAPTCHA не загружается, не проверяется и ничего не отправляет;
- OIDC, PKCE, web redirect, deep link и CAPTCHA API не реализуются;
- текущие вход и восстановление пароля продолжают работать по существующей мобильной схеме.

SSO и CAPTCHA считаются временными визуальными заглушками, а не готовым функционалом.

Полная реализация SSO и CAPTCHA обязательна отдельным этапом после подключения нового backend. Для CAPTCHA необходимо подключить получение задания, обновление, ввод/проверку ответа и передачу подтверждения в авторизацию и восстановление пароля. Для SSO необходимо согласовать и реализовать backend-контракт, OIDC/PKCE, системный переход, возврат в приложение через deep link, получение токена, ошибки и отмену входа.

### Отложенная идея сохранения данных для входа

Сохранение логина и пароля через системное защищённое хранилище обсуждалось как отдельная будущая возможность. Оно не является эталоном текущей UI-миграции: единственный UI-источник — актуальная ветка `api-laravel` проекта `jaco_driver_site`.

Для курьерского приложения такой сценарий логичен на странице авторизации, но не входит в текущий визуальный перенос и требует отдельного согласования, потому что добавляет нативную зависимость и меняет auth/store/startup-поведение. Предпочтительный вариант:

- никогда не сохранять пароль в `AsyncStorage`;
- после успешного входа отдельно спрашивать разрешение на сохранение в Keychain/Keystore;
- при следующем открытии авторизации сначала предлагать использовать сохранённые данные;
- запрашивать системное подтверждение пользователя только после его согласия;
- подставлять логин и пароль в поля без автоматической отправки формы;
- предусмотреть обновление и удаление сохранённых данных.

### Отложенный вопрос к руководителю. Сохранение данных для входа

Статус: `обсудить с руководителем вместе с вопросом о платёжной QR-кнопке`.

После нажатия «Выйти» приложение очищает авторизованную сессию и возвращает пользователя на экран входа. Ранее экран авторизации оставался смонтированным и сохранял логин и пароль в локальном состоянии формы; это исправлено очисткой чувствительных полей сразу после успешного входа. Исправление не является механизмом сохранения учётных данных и не заменяет отдельное решение руководителя.

Необходимо получить решение руководителя:

1. реализовать явное предложение сохранить данные для следующего входа, как в приложении магазина, используя только системное защищённое хранилище Keychain/Keystore и согласие пользователя;
2. определить поведение после «Выйти»: предлагать ранее сохранённые данные либо всегда показывать пустые поля;
3. выбрать способ интеграции: системный Password Manager/Autofill или собственный экран предложения поверх Keychain/Keystore;
4. если сохранение не требуется — гарантированно очищать логин и пароль при выходе.

До решения руководителя не добавлять постоянное хранение пароля и не сохранять его в `AsyncStorage`. Текущее сохранение значений только в состоянии формы нужно рассматривать отдельно от безопасного хранения данных для будущих входов.

### Визуальное соответствие

Эталоном является мобильный вид сайта, а не его desktop-компоновка. Для каждого экрана учитываются:

- светлое и тёмное состояния, если они есть на сайте;
- начальное, заполненное, loading, empty и error-состояния;
- размеры, отступы, радиусы, цвета, тени, типографика и иконки;
- клавиатура, прокрутка, Safe Area, Status Bar и нижняя системная область;
- допустимые различия нативных контролов Android и iOS.

Допустимое отличие от сайта должно быть записано в разделе соответствующего этапа, а не приниматься молча.

### Бизнес-поведение

Визуальный перенос сам по себе не разрешает:

- менять формат запросов авторизации;
- переносить web cookie-session в мобильное приложение;
- переписывать глобальный store;
- менять правила действий с заказами;
- менять GPS-условия;
- менять карту или навигацию за пределами согласованного UI-этапа.

### SMS-код и переход на новый backend

Текущее мобильное приложение использует legacy API `https://api2.jacochef.ru/driver/public/index.php/` и методы `auth → get_sms/check_code`. Этот backend фактически отправляет четырёхзначный SMS-код, поэтому до миграции API экран восстановления принимает ровно 4 цифры.

Новый сайт использует REST API `https://apidriver.jacochef.ru/api/v1/...` и шестизначный SMS-код. При отдельном переходе мобильного приложения на новый backend необходимо снова изменить ограничение поля и проверку кода с 4 на 6 цифр. Подключение нового backend не входит в текущую UI-миграцию и должно выполняться отдельным согласованным этапом вместе с проверкой контрактов авторизации, токена и остальных запросов.

Страница статистики уже существует в мобильном приложении и зарегистрирована как маршрут `Statistics`, но её пункт в drawer условно скрывается настройкой `driver_page_stat_time`. Текущий legacy API `api2.jacochef.ru` возвращает для приложения отключённое значение, тогда как новый сайт получает настройки с `apidriver.jacochef.ru` и показывает пункт. На время UI-проверки пункт принудительно доступен только в dev-сборке через `__DEV__`; в release-сборке продолжает действовать backend-флаг. После подключения нового backend необходимо проверить полученное значение флага, появление пункта «Статистика» в drawer и доступность самого экрана, затем удалить временное dev-условие.

28.08.2026 на текущем legacy API подтверждена backend-проблема восстановления пароля:

- `get_sms` вызывается один раз с 11-значным номером и возвращает `st: true`;
- пользователь получает четырёхзначный SMS-код;
- `check_code` получает тот же 11-значный номер и код длиной 4 цифры;
- backend отвечает `st: false` и текстом «Код из смс введен не верно»;
- клиент не меняет цифры кода и корректно передаёт параметры, поэтому проблема оставлена до отдельного backend-этапа.

Чек-лист этапа подключения нового backend:

- заменить legacy-вызовы `auth → get_sms/check_code` на REST-маршруты нового `apidriver`;
- сверить контракты входа, восстановления пароля, токена, ошибок и CAPTCHA;
- заменить визуальную CAPTCHA полноценной интеграцией в авторизации и восстановлении пароля: получение, обновление, проверка и обработка ошибок;
- заменить визуальную кнопку SSO полноценным сценарием входа после согласования backend-контракта, OIDC/PKCE, redirect/deep link и обмена на токен;
- изменить ограничение и валидацию SMS-кода с 4 на 6 цифр;
- проверить отправку, хранение, срок действия и подтверждение последнего SMS-кода;
- проверить полный сценарий смены пароля и последующего входа;
- проверить `driver_page_stat_time`, появление пункта «Статистика» в drawer и переход на экран;
- подключить на странице «Настройки» настоящий выбор кафе после появления в новом API `point_id`, списка доступных точек и метода сохранения выбранной точки;
- удалить временные dev-логи `[AUTH-RECOVERY]` после диагностики и стабилизации backend.

## 3. Базовые параметры эталона авторизации

Мобильный эталон проверен при viewport `390 × 844`:

- внешние отступы: `14–16`;
- карточка: радиус `24`, внутренние отступы `24 × 20`;
- логотип: около `84 × 84`;

- поля: высота `58`, радиус `18`;
- кнопки: высота `52`, радиус `18`;
- основной градиент: `#CC0033 → #A6002A`;
- фон: светлый серо-белый градиент с мягкими декоративными пятнами.

Логотип сайта и [src/shared/assets/logo.png](../src/shared/assets/logo.png) бинарно совпадают. Старый [src/shared/assets/wallpaper.png](../src/shared/assets/wallpaper.png) не является частью нового UI авторизации.

Эти значения — исходная точка для нативной адаптации, а не требование использовать CSS-пиксели напрямую.

### Отложенная задача. Светлая и тёмная темы после нового backend

Статус: `отложена до этапа подключения нового backend`.

Причины вынесения в отдельную задачу:

- сайт хранит настройку интерфейса в отдельном поле `dark_theme`, которого нет в контракте текущего мобильного legacy API;
- существующее поле приложения `theme` отвечает за оформление маркеров карты, а `night_map` — только за ночной режим карты, поэтому использовать их для темы всего приложения нельзя;
- в текущей ветке `api-laravel` файл `pages/_app.tsx` импортирует отсутствующий `shared/styles/createAppTheme.ts`, поэтому реализацию сайта сначала нужно получить в полном и проверенном виде;
- временное локальное хранение темы в мобильном приложении создало бы отдельное поведение, которое затем пришлось бы заменять при миграции backend.

Перед началом отдельной задачи необходимо:

- подключить новый backend и подтвердить контракт чтения и сохранения `dark_theme`;
- получить отсутствующий `createAppTheme` в актуальной ветке сайта;
- добавить отдельное состояние темы приложения, не связанное с темой маркеров и `night_map`;
- подключить режим к Gluestack, общей палитре, навигации, Safe Area и Status Bar;
- переносить тёмные состояния поэкранно и проверить их на Android и iOS.

### Отложенный вопрос к руководителю. Платёжная QR-кнопка

Статус: `обсудить с руководителем перед завершением UI-миграции`.

В текущем мобильном приложении и доступной Git-истории отсутствуют обработчик QR-кнопки, `actionPayOrder`, запрос `get_pay_qr`, платёжная модалка, проверка оплаты и подключение `driver_pay` из ответа API. На актуальном сайте платёжный сценарий подключён для карточки заказа на карте, но не подключён на странице списка заказов.

Необходимо получить решение руководителя:

1. переносить в приложение полный платёжный QR-сценарий вместе с новым backend;
2. временно скрыть неработающую QR-кнопку до появления поддерживаемого API.

До решения руководителя функциональность QR не реализовывать и не придумывать поведение на legacy API.

## 7. Процесс одного UI-этапа

1. Оркестратор выбирает один пункт этого плана.
2. Аналитик фиксирует источник, состояния, `In scope now`, `Out of scope` и критерии приёмки.
3. Пользователь отдельно разрешает изменения кода для этого пункта.
4. Разработчик выполняет только согласованный scope.
5. Тестировщик формирует короткий чек-лист состояний и рисков для проверки пользователем, но сам не запускает приложение и тесты.
6. Ревьюер статически сравнивает дифф со всем актуальным связанным кодом `jaco_driver_site` на ветке `api-laravel` и проверяет отсутствие придуманных или лишних изменений без запуска приложения.
7. Приложение, `lint`, `typecheck`, unit-тесты и ручной smoke Android/iOS после правок запускает пользователь.
8. Пользователь сообщает результат визуальной и технической проверки, после чего статус и оставшиеся отличия записываются в этот документ.
9. Коммит делает пользователь.

## 9. Definition of Done UI-миграции

UI-миграция завершена, когда:

- все пункты карты экранов имеют финальный статус;
- ключевые состояния визуально сопоставлены с сайтом;
- согласованные отличия записаны;
- SSO и CAPTCHA остаются явно обозначенными визуальными заглушками;
- существующая бизнес-логика не изменилась без отдельного согласования;
- Safe Area и Status Bar проверены на Android и iOS;
- светлая тема перенесена в рамках текущих экранов; тёмная тема ведётся отдельной задачей после подключения нового backend;
- решение руководителя по платёжной QR-кнопке зафиксировано и выполнено;
- решение руководителя по сохранению данных для входа и поведению полей после «Выйти» зафиксировано и выполнено;
- пользователь подтвердил результат `lint`, `typecheck` и `test:unit`;
- пользователь подтвердил Android/iOS release smoke либо зафиксировал его блокер;
- пользователь подтвердил проверку на реальных устройствах либо зафиксировал её блокер.
